# Demo 前端重构方案：从七个展厅到一条时间线

状态：方案稿 v1（2026-10-25）。实施前需确认；不破坏零依赖原则。

## 0. 诊断：为什么现在"太复杂"

现状：7 个并列视图（ledger / record / brief / search / context / evidence / safety）、
563 行 HTML、1596 行 JS（40+ 函数 + 全量双语 i18n）、649 行 CSS。

复杂度的三个根源：

1. **按子系统组织，不按任务组织。** 五个视图各自展示一个引擎能力（简报、检索、
   RAG、证据、安全），用户被迫先理解系统架构才能用产品——这是"控制面板"，
   不是"产品"。
2. **学习单元太多。** 7 个导航项 = 7 套表单、指标卡和说明面板；教学文案与操作
   混排在同一屏，信息密度居高不下。
3. **主线被平铺。** 项目真正的灵魂交互（冲突拒写 → 显式拍板）只是七个并列
   视图之一，没有被结构放大。

## 1. Kimi 的设计思想 → 本方案的原则

来源：Kimi 官方品牌手册（kimi.com/resources/kimi-brand）与产品实践。

| Kimi 原则 | 本方案的落地 |
|---|---|
| **De-coding（解码）**：把复杂 AI 能力呈现为普通用户可解码的形态 | 状态机解码为四个中文词：**算数 / 已替代 / 有争议 / 待复审**；一条声明一行字，无行话 |
| **少而深**：把一个能力做到极致，胜过十个平庸功能 | 视图 7 → 1.5：一条**项目时间线** + 一个可折叠的**开发者抽屉**。主线只讲一个故事：换 Agent 续作 |
| **对话为核心、单一主入口** | 记录是 hero：页面底部一个输入框"记一条决定…"，像 Kimi 的输入框一样等待 |
| **科技的严谨 + 人文的温度** | 暖白底（非冷蓝灰）、大留白、圆角卡片；但字节预算、省略计数等数字永远如实展示，绝不美化 |
| **数据可视化克制且绝不误导** | 时间线用中性灰为底、电光蓝（#007CFF）只给"算数"；已替代不删除只是沉下去 |

### 视觉语言（对齐品牌手册）

- **色板**：主锚 `#007CFF`，深蓝 `#002F5B`，浅蓝 `#A0DAF7`；中性阶
  `#121212 / #707070 / #C3C3C3 / #E1E3E6 / #FFFFFF`；底色暖白（#FAFAF8 系）。
  点缀色仅用于状态：有争议 `#F4F9A7`（黄）、待复审 `#FFD1D4`（粉）、
  已替代用中性灰。
- **字体**：品牌用 Inter / Geist Mono / Sentient。Demo 保持零网络，故用
  系统字体栈近似：`system-ui`（≈Inter）、`ui-monospace`（≈Geist Mono，用于
  claim id、字节、时间戳）。不引入 CDN 字体，不破零依赖。
- **节奏**：8px 基准网格；一屏至多一个主动作。

## 2. 目标信息架构

```
┌──────────────────────────────────────────────┐
│ ◉ Atlas API 项目              现在 ▾   [中|EN]│  顶栏：项目 + 点时切换 + 语言
├──────────────────────────────────────────────┤
│                                              │
│  现在什么算数 (3)                             │  ← 电光蓝圆点，一行一条
│  ● 数据库统一使用 PostgreSQL        database │
│  ● API v1 保持冻结                       api │
│  ● 部署脚本不再写生产库                 ops   │
│                                              │
│  ⚠ 需要你 (2)                                │  ← 黄/粉，折叠区
│    有争议：超时责任归属                        │
│    待复审：PG 方案（前提已坍塌）               │
│                                              │
│  已替代 (6) ▸                                 │  ← 中性灰，默认折叠
│                                              │
├──────────────────────────────────────────────┤
│ [ 记一条决定…                          ] 记录 │  hero 输入框
└──────────────────────────────────────────────┘
   * 开发者视图（简报原始包 / 检索 / RAG / 安全）→ 底部「开发者」链接展开抽屉
```

要点：

1. **一条时间线就是台账本身**。三段式（算数 / 需要你 / 已替代）把 v1 的
   ledger + brief 两个视图合并；简报不再是一个页面，而是时间线顶部的一个
   **预算条**（2048 B 默认，装不下如实显示"省略 N 条"）。
2. **点时简报做成顶栏的"现在 ▾"下拉**：选"上个月"，整条时间线切到当时的
   世界——阶段 A 的 `--at` 能力第一次有了 UI，也是"换 Agent 续作"叙事的
   关键道具（新 Agent 开场第一问：之前什么算数？）。
3. **冲突拒写是时间线上的内联事件**，不再是弹窗表单流：输入冲突文本 → 输入框
   上方展开"冲突摊开卡"，两个按钮——**替代旧的** / **记为有争议**。
   灵魂交互保留，路径从 4 步缩到 2 步。
4. **有争议可收场**：争议条目上的「收场」入口（维持/撤回/新决定三选），
   阶段 A 的 resolve 第一次有了 UI。
5. **开发者抽屉**收纳 brief 原始 JSON、检索对比（状态过滤开关）、RAG 证据、
   安全操作——功能一个不删，但退出主线，不再对首次访问者收门票。
6. **开场叙事**：首屏顶部一句话——"周五在豆包定的方案，周一的 Codex 接着干。
   这个页面就是两台 Agent 之间那份'什么才算数'。" 种子场景时间线里预置
   一条"来自豆包导入"的声明，让跨 Agent 续作从第一眼可见。

## 3. 工程方案

| 项 | 现状 | 目标 |
|---|---|---|
| 视图 | 7 个 section + 路由 | 1 个时间线 + 抽屉；删掉视图路由层 |
| index.html | 563 行 | ~220 行（单结构） |
| app.js | 1596 行 / 40+ 函数 | ~750 行：渲染时间线、冲突流、预算条、i18n、抽屉 |
| styles.css | 649 行 | ~420 行，新色板令牌（CSS variables） |
| i18n | 全量双语文案字典 | 主线文案减 60%，行话词表化（状态四词 + 动作词） |
| server.py | 693 行 | 不动（API 兼容；新增 resolve 与 at 端点透传） |

实施顺序（每步可独立提交、测试保护下进行）：

1. **色板与排版令牌**（styles.css 重写，HTML 结构不动）——先让气质到位；
2. **信息架构合并**：ledger+brief → 时间线三段式 + 预算条 + "现在 ▾"；
3. **hero 输入框与内联冲突流**：record 视图退役；
4. **开发者抽屉**：search/context/evidence/safety 迁入；
5. **叙事注入与阶段 A UI**（待复审区块、争议收场、豆包种子）；
6. 全量测试（test_demo.py 适配新 DOM）+ 双语检查。

## 4. 验收标准（Kimi 式，可检验）

1. **3 秒**：新用户不读文档能说出这个页面是什么（一句话主标题 + 三段式时间线）；
2. **5 秒**：完成第一次记录（一个输入框，回车即记）；
3. **2 步**：冲突摊开到显式拍板的路径不超过两次点击；
4. **零行话**：界面不出现 claim/supersede/dispute/brief 英文术语；
5. **数字诚实**：预算、省略、计数与 CLI 输出逐字一致（沿用 demo 测试的对照断言）；
6. **零网络**：无外部字体/框架/请求，离线可跑（品牌字体用系统栈近似，方案内说明）。

## 5. 明确不做的事

- 不引入前端框架（React/Vue）——零依赖是产品立场，不是技术债；
- 不做用户系统/多项目切换——demo 是一次性单用户视图，边界不变；
- 不动 server 的 API 形状——CLI/MCP/demo 共用引擎的架构不动摇。
